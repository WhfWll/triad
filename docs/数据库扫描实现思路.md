# 数据库扫描实现思路

> 本文档描述 Triad 平台「数据安全」模块中**数据库安全检查**与**敏感数据发现**两类扫描能力的当前实现思路、代码结构与扩展方向。  
> 对应需求文档 `docs/需求.md` 第 3 章「数据安全检查」。

---

## 一、能力概览

数据安全模块包含两条独立的扫描链路，共用任务框架与连接层，但检测目标与引擎不同：

| 能力 | 任务类型 | 核心问题 | 主要引擎 |
|------|----------|----------|----------|
| **数据库安全检查** | `TaskTypeDataSecDB` (4) | 实例配置是否合规、版本是否存在已知 CVE | `DBBaselineChecker` |
| **敏感数据发现** | `TaskTypeDataSecSensitive` (5) | 库表字段是否存储敏感个人信息 | `SensitiveDataFinder` |

**支持的数据库类型（5 种）**：

| dbType | 数据库 | 连接实现 |
|--------|--------|----------|
| 1 | MySQL | `database/sql` + go-sql-driver |
| 2 | PostgreSQL | TCP 探测（完整 SQL 基线待补 `lib/pq` 驱动） |
| 3 | MongoDB | HTTP 探测（`/`, `/buildInfo` 等） |
| 4 | Redis | go-redis 协议 |
| 5 | CouchDB | HTTP REST |

**并发限制**：数据安全任务异步执行，信号量上限 **5**（`dataSecMaxConcurrentDB`）。

## 三、任务模型

与应用安全、主机安全一致，采用 **Task + Target** 模型，**支持单任务多目标**：

1. 用户提交扫描请求（`targets[]` 可含多个数据库实例）→ 创建 `task_task`（`task_type = 4 或 5`）
2. 每个目标写入一条 `task_target`，连接信息独立存于各 target 的 `task_template_json`
3. 后台 goroutine 异步执行（并发上限 5），逐 target 扫描
4. 扫描结果带 `target_id` 写入结果表；详情页可按目标筛选

**多目标请求示例**：

```json
{
  "name": "生产库批量基线",
  "dbType": 1,
  "targets": [
    { "dbHost": "10.0.0.1", "dbPort": 3306, "dbName": "app", "dbUser": "scan", "dbPassword": "***" },
    { "dbHost": "10.0.0.2", "dbPort": 3306, "dbName": "app", "dbUser": "scan", "dbPassword": "***" }
  ]
}
```

仍兼容旧版单目标字段（`dbHost` / `dbPort` / …），未传 `targets` 时自动转为单元素数组。

**单目标连接配置 JSON 结构**（`datasecTaskConfig`，存于各 target）：

```json
{
  "dbType": 1,
  "dbHost": "192.168.1.10",
  "dbPort": 3306,
  "dbName": "app_db",
  "dbUser": "scanner",
  "dbPassword": "***",
  "dataTypes": [1, 4, 5],
  "scanAllDb": false
}
```

敏感数据扫描额外使用 `dataTypes`（限定敏感类型）与 `scanAllDb`（是否扫描全部库）。

## 四、数据库安全检查（基线 + CVE）

### 4.1 执行入口

```
POST /smart/datasec/db/run
  → application.DataSecScan.RunDBCheck
  → runDataSecTask (异步)
  → runDBBaselineForTarget
  → services.DBBaselineChecker.RunDBCheck
```

### 4.2 扫描三阶段

`RunDBCheck` 在成功连接目标库后，按顺序执行三个阶段：

```
阶段 1：配置基线检查（SQL / 命令规则）
    │
    ├─ 加载规则：datasec_rule 表优先，否则内置规则
    ├─ 过滤 KnowledgeOnly=true 的规则（cve_kb 类型不参与执行）
    ├─ 逐条执行 queries，比对 matchType 期望值
    └─ 写入 db_check_result（通过 / 不通过 / 错误）

阶段 2：版本探测
    │
    ├─ MySQL:     SELECT VERSION()
    ├─ Redis:     INFO server → redis_version
    ├─ MongoDB:   GET /buildInfo 或 /
    ├─ CouchDB:   GET / → version 字段
    └─ PostgreSQL: SHOW server_version（依赖驱动完善）

阶段 3：CVE 版本匹配
    │
    ├─ 从 default-cve.db 按库型筛选 CVE（最多 800 条）
    ├─ 用 CPE 配置与实例版本做范围比对 (MatchCpe)
    ├─ 命中写入 db_check_result（最多 50 条，标记为 CVE 项）
    └─ 无命中时写入一条「CVE 版本匹配 · 通过」摘要
```

### 4.3 规则来源与优先级

| 来源 | 存储 | 是否在线执行 | 说明 |
|------|------|--------------|------|
| **datasec_rule 表** | MySQL | 是（`matchType != cve_kb`） | 启动时 / 手动 reload 加载到内存 |
| **内置规则** | Go 代码 | 是 | 库表无启用规则时的兜底（`getBuiltinDBBaselineRules`） |
| **CVE 导入规则** | datasec_rule | 否（`matchType = cve_kb`） | 知识库条目，满足 3800+ 规则规模指标；**实际漏洞判定靠阶段 3 在线 CPE 匹配** |

**规则加载逻辑**（`services/datasec_rules_engine.go`）：

```
InitDatasecRulesFromDB / ReloadDatasecRulesFromDB
  → 读取 datasec_rule WHERE enabled=1
  → 按 dbType 分组缓存到 datasecRulesByDB
  → getDBBaselineRules(dbType) 优先返回库规则，否则内置
```

**matchType 与判定函数**：

| matchType | 含义 |
|-----------|------|
| `contains` | 输出包含期望值（默认） |
| `exact` | 输出与期望值完全相等 |
| `not_contains` | 输出不包含期望值 |
| `empty` | 输出为空（常用于「不应有记录」类检查） |
| `always` | 始终通过（信息类） |
| `cve_kb` | 知识库型，跳过 SQL 执行 |

### 4.4 基线检查类别

对应枚举 `tools/enums/baseline.go`：

| category | 名称 | 典型检查项 |
|----------|------|------------|
| 1 | 身份认证 | root 空密码、skip_grant_tables |
| 2 | 权限控制 | 匿名账户、远程 root、SUPER/FILE 权限 |
| 3 | 配置安全 | local_infile、test 库、sql_mode |
| 4 | 审计日志 | log_error、general_log |
| 5 | 网络安全 | 监听地址、默认端口 |
| 6 | 加密 | SSL/TLS |
| 7 | SQL 注入 | secure_file_priv 等 |
| 8 | 敏感数据识别 | （预留，与敏感数据扫描互补） |

### 4.5 CVE 匹配细节

- **CVE 库路径**：`services/cve_db.go` → `ResolveCveDBPath()`，依次尝试 `data/default-cve.db`、工作目录、可执行文件目录等
- **筛选条件**：`services/datasec_cve_import.go` 中 `datasecCveWhereClause`（mysql/postgresql/mongodb/redis/couchdb 等产品关键词）
- **版本比对**：`CveDB.MatchCpe(version, cpe_configurations)`，支持 CPE 版本区间（start/end including/excluding）
- **结果标识**：`RuleID >= 100000` 或描述含 `CVE 版本匹配`，详情 API 返回 `isCve: true`

### 4.6 风险汇总

- 单条检查项：`RiskLevel` 0~3（严重 / 高 / 中 / 低）
- 任务级风险：所有**不通过**项中取最严重映射到 `task_task.risk_level`
- 详情统计：`criticalCount` / `highRiskCount` / `middleRiskCount` / `lowRiskCount` 仅统计不通过项

## 五、敏感数据发现

### 5.1 执行入口

```
POST /smart/datasec/sensitive/run
  → application.DataSecScan.RunSensitiveScan
  → runSensitiveForTarget
  → services.SensitiveDataFinder.RunScan
```

### 5.2 扫描思路

与基线检查不同，敏感数据扫描关注**业务数据内容**，而非实例配置：

```
1. 连接目标库
2. 确定待扫描库列表（单库 或 scanAllDb 时 SHOW DATABASES）
3. 遍历每张表 → 读取 INFORMATION_SCHEMA 列信息
4. 对文本类型列，按字段名匹配敏感规则（FieldNames）
5. 抽样 SELECT … LIMIT 5，用正则 Pattern 校验样例值
6. 命中写入 sensitive_data_result
7. 汇总 highCount / mediumCount / lowCount / totalCount
```

### 5.3 内置敏感类型（8 类）

定义于 `services/sensitive_data.go` 的 `sensitiveRules`：

身份证号、银行卡号、护照号、手机号、邮箱、地址、出生日期、姓名等。

每种类型包含：

- `Pattern`：内容正则（可为 nil，仅依赖字段名）
- `FieldNames`：列名关键词（如 `phone`, `mobile`, `身份证`）
- `Level`：高 / 中 / 低敏感

### 5.4 与基线检查的区别

| 维度 | 数据库安全检查 | 敏感数据发现 |
|------|----------------|--------------|
| 扫描面 | 系统表、全局变量、权限表 | 业务库表与字段 |
| 规则 | datasec_rule + 内置基线 + CVE | 代码内置敏感规则 |
| 结果表 | `db_check_result` | `sensitive_data_result` |
| 核心指标 | 风险等级、CVE 命中 | 发现条数、敏感等级分布 |

| 字段 | 说明 |

## 十、启动依赖

`smart.go` 启动时需初始化：

1. `services.InitDatasecRulesFromDB` — 加载 datasec_rule
2. `services.InitCveDB` — 加载 default-cve.db（日志：`CVE database loaded: ...`）
3. `services.EnsureDatasecRuleTable` — 确保规则表存在

若 CVE 库缺失，基线 SQL 检查仍可运行，阶段 3 CVE 匹配会跳过并记录原因。

## 十一、当前限制与后续增强

| 项 | 现状 | 建议方向 |
|----|------|----------|
| PostgreSQL 基线 | 仅 TCP 连通性，SQL 未真正执行 | 引入 `lib/pq`，补全 SHOW/系统 catalog 规则 |
| MongoDB / CouchDB 基线 | 部分规则为占位（CheckFunc 恒 true） | 对接 admin 命令或 REST 配置接口 |
| CVE 覆盖 | 单次最多扫 800 条、展示 50 条命中 | 按版本预过滤、分页、与 datasec_rule 中 cve_kb 联动 |
| SQL 注入类 | 以配置项为主（secure_file_priv 等） | 增加受控探测或只读语句审计 |
| 敏感数据 | 8 类内置规则，MySQL 为主 | 支持更多类型、采样率配置、脱敏策略 |
| 结果导出 | 未实现 | 对接需求中的审计日志 / 报告导出 |

## 十三、典型使用流程

```
1. 【可选】数据安全 → 检测规则 → 同步内置规则 / 导入 CVE
2. 数据安全 → 任务管理 → 数据库安全检查 → 新建任务
3. 填写连接信息 → 【连接测试】→ 提交
4. 等待任务状态变为「已完成」
5. 点击「详情」→ 查看概览 / 基线检查项 / 版本漏洞(CVE)
6. 根据修复建议加固实例，必要时重新扫描验证
```

敏感数据发现流程类似，在「敏感数据发现」Tab 创建任务，详情中查看类型分布与敏感字段列表。
