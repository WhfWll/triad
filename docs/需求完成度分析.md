## 二、"审查结果导出"能力评估

需求原文：`具备审查结果导出能力，可以生成审计日志。`

这句话实际上包含**两个独立的能力要求**：
1. **审查结果导出** — 将扫描/检查的结果数据导出为外部文件（CSV、TXT、PDF 等）
2. **生成审计日志** — 对用户的操作行为（创建扫描、导出报告等）记录审计日志

### 2.1 导出能力现状

#### 主机安全（❌ 无导出）

| 功能模块 | 导出能力 | 说明 |
|----------|:--------:|------|
| 安全配置核查（基线） | ❌ | 有结果列表、详情，无导出接口 |
| CVE 漏洞扫描 | ❌ | 有发现列表、统计，无导出接口 |
| 恶意代码检测 | ❌ | 有扫描结果列表，无导出接口 |
| YARA 恶意代码检测 | ❌ | 有扫描结果列表，无导出接口 |

#### 应用安全（❌ 无导出）

| 功能模块 | 导出能力 | 说明 |
|----------|:--------:|------|
| 动态扫描 | ❌ | 有任务列表、详情，无导出接口 |
| 专项应用检测 | ❌ | 有任务列表、详情，无导出接口 |

#### 数据安全（⚠️ 部分具备）

| 功能模块 | 导出能力 | 说明 |
|----------|:--------:|------|
| 目标库管理 | ✅ 已具备 | 已有 `GET /datasec/target/export` 接口，可导出目标库列表 |
| 数据库基线检查结果 | ❌ | 有检查结果详情页，无导出接口 |
| 敏感数据扫描结果 | ❌ | 有扫描结果详情页，无导出接口 |
| CVE 检测结果 | ❌ | 有检测结果列表，无导出接口 |

### 2.2 审计日志能力现状

#### 审计日志基础设施（✅ 完整）

| 组件 | 状态 | 说明 |
|------|:----:|------|
| `log_audit` 表 | ✅ | 已建表，包含 log_type / content / username / ip / create_time 等字段 |
| `LogAuditAdd` | ✅ | 写入方法可用 |
| `LogAuditList` | ✅ | 列表查询可用，支持按类型/内容/时间筛选 |
| `LogAuditEmpty` | ✅ | 过期自动清理（可按配置的天数） |
| 前端页面 | ✅ | 有审计日志查看页面，支持分类筛选 |
| 路由注册 | ✅ | `/logs/logauditlist`、`/logs/logauditempty` 等完整注册 |

#### 当前写入审计日志的场景（仅 2 处）

| 场景 | 状态 | 说明 |
|------|:----:|------|
| 用户登录 | ✅ | 多种登录方式均写入 `LogAuditTypeLogin` 审计日志 |
| 任务创建 | ✅ | 通过 `SendTaskInfoToAuditLog` 写入 `LogAuditTypeOperate` 日志 |
| **三大安全模块操作** | **❌** | **安全配置核查、CVE 扫描、YARA 检测、应用安全扫描、数据库检查、敏感数据扫描等均未写入审计日志** |

#### 缺失审计日志的具体场景

| 模块 | 未记录的操作 | 影响 |
|------|------------|------|
| 主机安全 | 运行基线检查、运行 CVE 扫描、运行 YARA 检测、查看结果、导出结果 | 无法审计谁在何时对哪些主机进行了安全检查 |
| 应用安全 | 创建动态扫描、创建专项检测、查看详情 | 无法审计谁在何时对哪些应用发起了扫描 |
| 数据安全 | 创建数据库检查、创建敏感数据扫描、查看结果、导出目标库 | 无法审计谁在何时执行了数据安全检查操作 |

## 七、当前最影响验收的未完成项

按优先级排序：

### 第一优先级：审查结果导出（3 个模块均缺失）

需求明确要求"具备审查结果导出能力"，但当前三大安全模块均**没有结果导出接口**。这是最直接影响验收的合规性问题。

| 模块 | 需要导出的内容 | 建议接口 |
|------|--------------|----------|
| 主机安全 | 基线检查结果、CVE 发现明细、YARA 检测结果 | 3 个 CSV 导出接口 |
| 应用安全 | 动态扫描漏洞、专项应用检测结果 | 2 个 CSV 导出接口 |
| 数据安全 | 数据库检查结果、敏感数据扫描结果 | 2 个 CSV 导出接口 |

### 第二优先级：操作审计日志缺失

需求明确要求"可以生成审计日志"，但当前三大安全模块的操作**都没有写入审计日志**。仅用户登录和普通任务创建有审计记录。

需要在各模块的关键操作节点（创建扫描、扫描完成、导出等）调用 `LogAuditAdd`。

### 第三优先级：数据安全多库深度不足

MongoDB（3 条）/ CouchDB（3 条）/ Redis（5 条）的基线规则数量与 MySQL（16 条）差距明显。

## 九、结论摘要

截至当前代码状态，产品在**规则规模**上已大幅改善，但在**审查结果导出**和**审计日志**这两个需求明确要求的能力上存在合规性缺口：

| 模块 | 完成度 | 关键变化 | 最大短板 |
|------|--------|----------|----------|
| 主机安全 | ~82% | 规则库丰富 | **无结果导出 + 无审计日志** |
| 应用安全 | ~80% | 7000+ 规则达标 | **无结果导出 + 无审计日志** |
| 数据安全 | ~72% | 规则库有补充 | **多库深度不足 + 无结果导出 + 无审计日志** |

审查结果导出和审计日志虽然实现成本不高（主要是新增接口和写入调用），但验收时是明确的"有/没有"的判定项，建议优先补齐。
