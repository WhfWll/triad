# 对外数据交互协议文档

本文档描述了 webScanner 在本地扫描（Webhook）和分布式扫描（gRPC）模式下，对外发送的数据类型、结构及含义。

## 1. 概述

扫描器主要通过两种方式对外输出数据：
1.  **Webhook 推送**：用于实时推送扫描日志、漏洞结果和状态变更。适用于单机/本地扫描模式，以及分布式节点的内部日志收集。
2.  **gRPC 接口**：用于分布式调度中心主动拉取扫描结果和状态。

---

## 2. Webhook 数据结构

所有通过 Webhook 推送的数据遵循统一的 JSON 结构 `ScannerLog`。

### 2.1 基础数据结构

```json
{
  "CreatedAt": 1678888888,          // 时间戳
  "Hash": "...",                    // 唯一哈希
  "content": "...",                 // 文本消息内容
  "pocname": "...",                 // 关联的 POC 名称 (可选)
  
  // 攻击路径追踪字段
  "call_chain_id": "...",           // 调用链 ID
  "parent_script_id": "...",        // 父节点 ID
  "script_execution_id": "...",     // 当前脚本执行 ID (自身 ID)
  "trigger_reason": "...",          // 触发原因
  "attack_path": ["id1", "id2"],    // 完整攻击路径 ID 列表
  
  "log_type": "...",                // 日志类型 (关键字段)
  "result": { ... }                 // 结构化结果数据 (根据 log_type 变化)
}
```

### 2.2 日志类型 (log_type) 详解

根据 `log_type` 字段的不同，`content` 和 `result` 字段的含义如下：

| log_type | 触发场景 | Content 含义 | Result / 附加说明 |
| :--- | :--- | :--- | :--- |
| `port_scan_start` | 端口扫描开始 | 描述扫描目标IP和端口范围 | - |
| `port_scan_result` | 发现开放端口 | JSON 字符串 (包含端口详情) | **重要**：Payload 为 `fp.MatchResult` 的 JSON 序列化字符串，包含 IP, Port, ServiceName 等。 |
| `root_dir_scan` | 根目录扫描 | 描述正在扫描的基础 URL | - |
| `root_dir_start` | 根目录扫描开始 | 同上 | 用于构建攻击路径树 |
| `crawlerx_start` | Web 爬虫/通用扫描开始 | 描述扫描的目标 URL | - |
| `second_dir_brute_start`| 二级目录爆破开始 | 描述正在爆破的基础 URL | - |
| `vulnerability_found` | 发现漏洞 | 漏洞简述 | `result` 字段包含完整的 `DetectionResult` 结构 (URL, Payload, Details 等) |
| `scan_start` | 整个任务开始 | 任务启动信息 | - |
| `scan_end` | 整个任务结束 | 任务结束信息 | - |

### 2.3 端口扫描结果结构 (port_scan_result)

当 `log_type` 为 `port_scan_result` 时，`content` 字段通常是一个 JSON 字符串，解析后结构如下：

```json
{
  "Target": "192.168.1.1",
  "Port": 80,
  "State": "open",
  "Fingerprint": {
    "ServiceName": "http",
    "Version": "1.0",
    "Info": "..."
  }
}
```

## 3. gRPC 接口数据结构

分布式模式下，客户端通过 `GetScanResults` 接口获取数据。

### 3.1 结果响应结构 (ResultResponse)

```protobuf
message ResultResponse {
  string task_id = 1;
  string results_json = 2;              // (已废弃或用于兼容)
  int32 total_count = 3;                // 结果总数
  ScanTaskInfo task_info = 4;           // 任务状态信息
  repeated DetectionResult detection_results = 5; // 结构化漏洞结果列表
  repeated string logs = 6;             // 原始日志列表 (可能包含 JSON)
  int32 current_offset = 7;             // 当前偏移量 (用于增量获取)
}
```

### 3.2 漏洞详情结构 (DetectionResult)

`detection_results` 列表中的每一项代表一个具体的漏洞或风险点：

```protobuf
message DetectionResult {
  string url = 1;                 // 漏洞 URL
  string parameter = 2;           // 漏洞参数
  string payload = 3;             // 攻击 Payload
  string payload_success_flag = 4;// 验证成功的特征
  string details = 5;             // 详细描述 (JSON 字符串)
  string script_name = 6;         // 脚本名称
  bytes request_raw = 7;          // 原始请求包
  bytes response_raw = 8;         // 原始响应包
}
```

### 3.3 分布式日志处理

在 gRPC 模式下，`logs` 字段通常会透传后端产生的 Webhook 日志。客户端在接收到 `logs` 数组后，应尝试将其作为 JSON 解析。如果解析成功且包含 `log_type` 字段，则可按照 **2.2 节** 的逻辑进行处理（例如在 UI 上绘制攻击路径树）。

### 3.4 分布式任务结束判定

分布式扫描的“任务结束”通过 gRPC 的任务状态来判定，当前实现不会主动发送 `scan_end` 的 Webhook 日志。判定与返回规则如下：

- 判定条件：服务端在执行完具体扫描流程并收集 Webhook 结果后，调用任务状态更新为 `completed`，进度为 `100`，并记录 `EndTime`。
- 返回位置：
  - 通过 `GetScanStatus` 接口可获取 `StatusResponse` 中的 `status=completed`、`progress=100`、`message="扫描完成"`。
  - 通过 `GetScanResults` 接口可在 `ResultResponse.task_info` 中获取完整的任务信息（包含 `start_time` 与 `end_time`）。
- 示例（TaskInfo 片段）：
  ```json
  {
    "task_info": {
      "task_id": "scan-task-001",
      "target": "http://example.com",
      "status": "completed",
      "progress": 100,
      "message": "扫描完成",
      "start_time": "2026-01-28 10:00:00",
      "end_time": "2026-01-28 10:12:34",
      "webhook_url": "http://127.0.0.1:8088/webhook"
    }
  }
  ```

说明：文档中提到的 `scan_end` 作为日志类型目前未在代码中主动发送；分布式模式下以 gRPC 的任务状态为准进行结束判定。

## 4. 数据用途分类指南 (标准协议)

为了方便第三方系统（或 AI 模型）对接处理，我们将返回的数据严格分为三类用途。每一类数据都有特定的 JSON 结构特征和关键字段。

### 4.1 画攻击路径图 (Attack Path Visualization)
用于构建扫描任务的执行拓扑树。通过节点间的父子引用关系，还原完整的攻击链路。

*   **用途**: 前端拓扑图绘制、攻击溯源。
*   **核心逻辑**: 使用 `script_execution_id` (本节点) 和 `parent_script_id` (父节点) 建立连接。
*   **关键字段**:
    *   `call_chain_id` (String): 全局唯一的调用链路 ID，同一次扫描任务中所有节点该值相同。
    *   `script_execution_id` (String): 当前节点的唯一标识 ID。
    *   `parent_script_id` (String): 父节点的标识 ID（根节点的父 ID 通常为空或特定标识）。
    *   `log_type` (String): 节点类型，决定节点的图标或样式。常见值：`port_scan_result`, `root_dir_start`, `vulnerability_found`。
*   **数据示例 (JSON)**:
    ```json
    {
      "log_type": "port_scan_result",
      "call_chain_id": "task-123456-chain-001",
      "parent_script_id": "",
      "script_execution_id": "node-port-80",
      "content": "Port 80 is open",
      "result": {
        "Ip": "192.168.1.1",
        "Port": 80,
        "ServiceName": "http",
        "ProductVerbose": "Nginx"
      }
    }
    ```

### 4.2 实时日志展示 (Real-time Logging)
用于在控制台或 UI 界面展示扫描的实时进度文本流。

*   **用途**: 用户界面控制台输出、任务状态监控。
*   **核心逻辑**: 只要包含 `content` 字段的数据均可作为日志展示。
*   **关键字段**:
    *   `content` (String): 人类可读的日志文本信息。
    *   `CreatedAt` (Int64): 日志产生的时间戳（秒）。
    *   `pocname` (String, Optional): 产生日志的模块或 POC 名称。
*   **数据示例 (JSON)**:
    ```json
    {
      "log_type": "scan_start",
      "content": "开始对目标 192.168.1.1 进行 Web 扫描...",
      "CreatedAt": 1706428800,
      "pocname": "web_manager"
    }
    ```

### 4.3 漏洞结果存储 (Vulnerability Storage)
用于持久化存储发现的确切漏洞详情，包含复现所需的请求响应包。

*   **用途**: 漏洞报告生成、数据库存储。
*   **核心逻辑**: 关注 `log_type` 为 `vulnerability_found` 的数据，或者直接提取 `result` 对象。
*   **关键字段**:
    *   `log_type` (String): 固定为 `vulnerability_found`。
    *   `result` (Object): 包含漏洞详情的核心对象。
        *   `url` (String): 漏洞 URL。
        *   `payload` (String): 攻击载荷。
        *   `payload_success_flag` (String): 验证成功的特征字符串。
        *   `request_raw` (String/Bytes): 原始 HTTP 请求包 (Base64 或 文本)。
        *   `response_raw` (String/Bytes): 原始 HTTP 响应包 (Base64 或 文本)。
*   **数据示例 (JSON)**:
    ```json
    {
      "log_type": "vulnerability_found",
      "script_execution_id": "vuln-node-001",
      "parent_script_id": "node-port-80",
      "content": "Found SQL Injection",
      "result": {
        "url": "http://192.168.1.1/login.php",
        "title": "SQL Injection in Login",
        "payload": "' OR 1=1 --",
        "payload_success_flag": "Welcome admin",
        "request_raw": "UE9TVCAv ... (Base64)",
        "response_raw": "SFRUUC8x ... (Base64)"
      }
    }
    ```

## 5. 关键流程示例

### 4.1 全扫描模式 (ScanAll) 数据流

1.  **启动**: 发送 `scan_start`。
2.  **端口扫描**:
    *   发送 `port_scan_start`。
    *   每发现一个端口，发送一条 `port_scan_result` (LogType) 数据。
3.  **Web 扫描 (针对每个端口)**:
    *   发送 `root_dir_start` / `root_dir_scan`。
    *   发送 `crawlerx_start`。
    *   爬虫运行中发现漏洞 -> 发送 `vulnerability_found` (或直接通过 gRPC 的 `DetectionResult` 返回)。
4.  **目录爆破**:
    *   发送 `second_dir_brute_start`。

### 4.2 Web 小智模式 (ScanWebXiaozhi) 数据流

1.  **启动**: 解析输入 URL。
2.  **强制端口记录**:
    *   即使不进行全端口扫描，也会构造并发送一条 `port_scan_result`，确保攻击路径树有一个根节点。
3.  **Web 扫描**:
    *   后续流程同 ScanAll 的 Web 扫描部分。
